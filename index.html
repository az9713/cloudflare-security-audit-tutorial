A practical guide for app developers

Hack your own app first

This guide explains common security problems in apps. It then explains how an AI security audit works, with Cloudflare's open-source security-audit skill as the example. Last, it explains how to build your own "vulnerability harness": a system that runs these audits at scale. You need app development experience. You do not need security experience.

Why this matters now

AI coding agents can read a large codebase quickly and test ideas about it all day without getting tired. Attackers use them too. The sources for this guide give these examples:

  • The FBI warned about a hacking agent that goes from a chosen target to full privileged access of the machine in less than 3 hours.
  • A researcher used a coding agent to find a critical vulnerability in the Java programming language in about 1 hour.
  • AI-assisted searches have found old bugs, such as a PHP vulnerability that had been there for years.

The defense is simple to state. Use the same AI method on your own app, and do it before an attacker does. Find the problems, prove them, and fix them before you release.

The one idea under all of security: the trust boundary

Every app has places where data or a request moves from someone you trust less to something you protect. Security people call each of these places a trust boundary. Most real vulnerabilities are a boundary where the check is missing, wrong, or can be bypassed.

Principal — any actor that can do things in your system: a logged-in user, an anonymous visitor, an admin, another service, a CI job, or an AI agent. A "lower-trust principal" is the actor with less authority on one side of a boundary.
Vulnerability — a flaw that lets a lower-trust principal do something it must not be able to do. Examples: read data, change data, run code, or stop a service. Exploit — the actual input or steps that use the flaw.
Authentication (often "authn") answers "who are you?" — login, passwords, sessions, API keys. Authorization (often "authz") answers "are you allowed to do this to this item?" Many bugs are endpoints that check authentication but forget authorization.

The five questions an attacker asks

The video gives five questions. They are not a complete list, but they cover most real problems in ordinary apps. An AI "hunter" (explained in tab 3) uses questions like these as its search frame. You do not need to know the answers yourself.

1. Can someone get in who shouldn't?

This is about authentication. Can someone log in without a valid password? Does a session stay valid after logout? Can someone guess a reset token? Does "remember me" last longer than you expect?

2. Can one user see another user's data?

This is about authorization and isolation. Can user A read or change user B's invoice by changing an ID in the URL? In a multi-customer (multi-tenant) app, can one customer see another customer's records?

3. Are passwords or API keys exposed?

This is about secrets. Is a key committed to the repository, printed in a log, returned in an error message, put in a URL, or sent to the browser in the JavaScript bundle?

4. Can a stranger trick the AI in your app?

This is prompt injection. If your app gives an AI model text from outsiders (a message, an email, a GitHub issue, a web page), that text can contain instructions. If the model follows them and has tools, the outsider controls those tools.

5. Can someone run up your bill or crash it?

This is resource exhaustion (also "denial of service", DoS). Can one request make your server do a huge amount of work? Can an anonymous user trigger paid AI calls without a limit? Can a queue grow until the service stops?

Common bug types, in plain language


Security people group bugs into attack classes: families of bugs that share a mechanism. The skill gives each class to a separate hunter. These are the core classes from the skill's ATTACK-CLASSES.md:

InjectionUntrusted input reaches a "sink" and is treated as code or commands.A search box value is pasted into a SQL query (SQL injection). A comment is shown as raw HTML and runs script in other users' browsers (XSS, cross-site scripting).

How prompt injection works


An AI model cannot reliably tell the difference between "instructions from the developer" and "text it was asked to read". If both go into the same prompt, the outsider's text can act as instructions.




What is NOT a vulnerability


Many automated scanners report "findings" that are not real problems. The skill is strict about this, and you should be too. These are not vulnerabilities on their own:


    
  
  • A missing best practice with no victim. Example: "the cookie has no HttpOnly flag", when no script on the page can be controlled by an attacker. That is a hardening note.
    • 
  
  • A missing second layer when the first layer works. If layer A stops the attack, the absence of layer B is a defense-in-depth gap, not a vulnerability.
    • 
  
  • Self-harm. A user who can delete their own data is using a feature, not crossing a boundary.
    • 
  
  • A "vacuous" finding. Cloudflare's example: "if a user has database write access, they can write to the database."
    • 
  
  • A crash reported as more than a crash. A parser crash is not "code execution" unless someone proves it.
    • 



The test for a real finding: name the lower-trust principal, the input it sends, the check that should stop it, the boundary that is crossed, and the concrete result for a real victim or resource.









The core method: one agent hunts, another tries to disprove


An agent here is an AI model running in a loop with tools (read files, search, run commands). A subagent is a separate agent that the main agent starts for one job. It has its own fresh memory (its own context window: the amount of text the model can hold at one time).


Attackers and defenders both use two roles:


    
  
  1. Hunter. It reads the code deeply and reports everything that could be a vulnerability, even when it is not confident. The goal is width. Real bugs are often subtle, so you do not want the hunter to filter too early.
    2. 
  
  2. Validator (the skill calls it a verifier). One new agent per candidate. Its only job is to prove the candidate is not a real bug. It cannot report new bugs of its own.
    3. 



Why separate them? Cloudflare's blog puts it this way: if a hunter grades its own homework, it will confidently validate everything it outputs. A fresh agent that did not form the theory does not want it to be true.





After validation, a survivor is still a theory based on reading code. The last step is to prove it: run a small test that shows the bad result. This test is called a proof of concept (PoC). Then you fix the code and keep the test, so the bug cannot return (a regression test).



What the skill is


A skill is a folder of instruction files that a coding agent (Claude Code, Codex, and others) loads when a request matches its description. The security-audit skill has 14 Markdown files (1,778 lines in total), a JSON schema for results, and two Node.js validator scripts with tests. It contains no attack tools. It contains method: what to look for, how to split the work, and what evidence is required.


It has two modes:


    
  
  • Guidance mode (the default). For a security question or a review of one area. It uses only the relevant parts and writes no files.
    • 
  
  • Full audit mode. Only when you explicitly ask to audit or pen-test a codebase, or ask for report files. It runs all six phases below.
    • 



In the skill's words, the parent is the main agent that coordinates the run. It is the only writer of the shared files. Hunters and verifiers each get their own folder and cannot change shared files, the target source, or each other's work.

The coverage ledger: how the audit knows what it has checked


An AI agent will say "I reviewed authentication" after reading two files. The skill does not accept that. It builds a coverage ledger: a JSON list of small work units. Each unit is one combination of:


    
  
  • surface: where input enters (for example the route POST /users/:id),
    • 
  
  • boundary: the control that protects it (for example requireOwner),
    • 
  
  • subsystem: the part of the code (for example packages/api),
    • 
  
  • attack class: the bug family to look for (for example access control).
    • 



A unit is "covered" only when a hunter returns the exact file paths it read and the checks it made. A unit with a possible bug is "candidate". A unit the hunter could not finish (for example, it needs to run code and there is no sandbox) is "blocked". After each wave of hunters, a fresh coverage critic agent looks for gaps: entry points with no unit, units closed with no evidence, missing paths. New units go into the next wave.

The ledger also makes cost countable: one unit is about one hunter assignment. A script, validate-coverage-ledger.cjs, checks the ledger after every update. It rejects, for example, a unit marked "covered" with no reviewed paths.



The three verdicts



  
confirmed
    
A complete source trace plus a bounded, observed result in a sandbox (for example, a dummy user got another dummy user's record). Only confirmed findings get a severity.

  
needs_validation
    
A source-grounded lead that cannot be settled from the code. It names the exact missing fact (for example "is this route behind the proxy's login in production?") and a safe plan to check it. It has no severity. It is not a "low-confidence confirmed bug".

  
rejected
    
The verifier disproved it. For example, a check further up the call stack stops the input. It is kept so that later runs do not re-report the same false claim.





Severity, briefly


Severity = how likely × how bad, based only on what was shown. The skill's anchors:




LevelAnchor in the skill


criticalAn unauthenticated actor gets code execution, full data-store access, or takeover of any account.


highAn actor fully defeats an explicit control with real consequences: authentication bypass, cross-tenant read/write, stored script that affects other users, authenticated code execution, or an unauthenticated remote stop of a shared service.


mediumA real boundary violation with limited reach, uncommon preconditions, or a narrow set of affected resources.


lowDisclosure of non-secret internals, or an effect that takes sustained effort for little gain.


informationalConfirmed, but minimal impact. Useful mostly as one step in a larger chain.




The skill's test between high and medium: does the result fully defeat a control for an action with real consequences, or only weaken it? If you cannot state the concrete damage, the severity is lower than it feels.



The sandbox rule


To prove a bug, you often need to run the target code. But the target code is untrusted. The repository could contain a malicious build script. So the skill runs target code only inside an OS-enforced sandbox: a box that the operating system enforces, not a box the agent promises to respect.



This is what Cole's prompt meant by "there is no OS-enforced sandbox available on this Windows machine, so do not execute any target code." The audit still runs. It reads code and validates by reading, and every lead that needs execution stays needs_validation.


The skill also never probes deployed endpoints, never uses real accounts, never spends paid API quota, and never runs load tests against a live service. It stops at the smallest effect that proves the defect.

What a confirmed record looks like


Every result is a JSON record that must match report-schema.json. A shortened example of a confirmed record (the field names are real, the values are illustrative):


{
  "verdict": "confirmed",
  "fingerprint": "auth/session-not-revoked-on-logout",
  "title": "Session cookie stays valid after logout",
  "root_cause": "logout clears the browser cookie but not the server session",
  "intended_behavior": "a logged-out session must be rejected",
  "trace": [
    {"kind": "entrypoint",  "file": "auth/routes.ts", "line": 40, "scope": "POST /logout", "description": "..."},
    {"kind": "propagation", "file": "auth/session.ts", "line": 88, "scope": "endSession",   "description": "..."},
    {"kind": "sink",        "file": "auth/routes.ts", "line": 61, "scope": "GET /verify",  "description": "..."}
  ],
  "conditions": [{"kind": "data_state", "description": "attacker holds a copy of an old cookie"}],
  "execution": {"attacker_perspective": "...", "payloads": ["..."], "instructions": ["..."],
                "observed_result": "GET /verify returned 200 after logout"},
  ...
}


A fingerprint is a stable name for the root cause. It must not contain a line number, a wave number, or a severity, so the same bug keeps the same name across runs and states. That is how runs are compared and how duplicates are merged.

Read REPORT.md first. It gives the profile and scope, a short summary, a table of confirmed findings, a separate needs-validation table, hardening notes, and coverage counts (covered, candidate, blocked, deferred).

  
Then act on each confirmed finding: write a test that shows the bug, fix it, and confirm the test now passes.

  
For each needs-validation lead: check the named fact (for example, a production setting), or run the suggested local test in a sandbox.







Run it again — and again


One run is not complete. In Cloudflare's tests, a single run found about half of the vulnerabilities that repeated runs found in total, and the ones it found were mostly the simpler ones. The skill is built for this. Each new run reads the earlier ledgers and findings, skips confirmed bugs whose code has not changed, re-checks bugs whose code changed, and sends the gaps to the hunters first.



How often



Cole's recommendation is one run before each release. Other options are every pull request, a fixed schedule (for example weekly), or after a security patch to a dependency or to your hosting. Google found that attackers sometimes turn security patches into attacks, because a patch shows where the old bug was.


Cloudflare runs its large harness as a periodic sweep, not on every pull request, because one full scan of a complex repository can take hours. Their longest took just over 14 hours. For per-PR checks, they recommend smaller, cheaper tools.



Rules to follow


    
  
  • Audit only your own code, or code you have written permission to test.
    • 
  
  • Do not let the agent probe your deployed app. The skill forbids it, and your prompt should repeat it.
    • 
  
  • Do not run target code without a real sandbox. On a normal Windows or Mac laptop with no sandbox, say so in the prompt, as Cole did.
    • 
  
  • Prove before you fix. A test that fails before the fix and passes after the fix is your evidence.
    • 
  
  • Treat needs_validation as a to-do list, not as confirmed bugs.
    • 










What a harness is


A harness is ordinary software around the AI model. It decides which tasks to run, starts agents, stores every result in a database, retries failures, and checks outputs with plain code. The model does the thinking for one small task at a time. The harness holds the memory and the rules.


Cloudflare started with a skill of about 450 lines on one repository and tuned the prompts until real bugs came out. In about six weeks they turned it into a harness that covers 128 repositories in Rust, Go, C, Lua, TypeScript, and Python. They say the prompts stayed nearly unchanged. The value is in the prompts. The harness is the plumbing that lets them run at scale.


Model-agnostic means the harness does not depend on one AI provider. Cloudflare says different models find different shares of the bugs, and providers change model behavior over time. So the harness is the part that lasts, and the model is a part you can swap.



Why a skill alone reaches its limits



  

    
1. Context runs out

    
    
After about an hour the context window fills. The agent then compresses its memory (compaction) and forgets bugs it was tracking. Fix: keep state outside the model, in a database. Treat the model as stateless.

  

  

    
2. A crash loses everything

    
    
One rate-limit error or network failure mid-run means starting over. Fix: save each result as soon as it exists, so a crash costs only the task in progress.

  

  

    
3. One repo cannot see others

    
    
A session in one repository does not see the apps that use it. Cloudflare found many bugs at the interface between components.

  




A fourth signal: coverage. One run finds about half of what many runs find. If your process becomes "run it ten times and compare by hand", you need a harness.

Cloudflare's full design: two systems, two models


The full system has two parts. The Vulnerability Discovery Harness (VDH) finds candidates. The Vulnerability Validation System (VVS) sorts, judges, and fixes them. Other tools can also feed findings into the VVS. Each part uses a different AI model, so the second model checks the first with different training and different blind spots.





VDH stages




StageJobDetail from the blog


ReconMap the architecture and likely threats.3 parallel recon subagents write architecture.md. Recon also writes a threat model (who could attack and how) for this repo. Beyond about 10 built-in attack classes, it can invent repo-specific classes with their own method.


HuntAttack one class at a time.Hunters compile code fragments, build small versions, and try to crash them in a sandbox built on unshare. Giving hunters a sandbox was the largest single quality gain.


ValidateCheck, then disprove.Two passes: plain code checks schema and file paths, then one isolated agent tries to disprove the finding.


GapfillFill thin coverage.Repos are divided into (area × attack-class) cells. Gapfill adds hunt tasks for cells that still look thin.


DedupMerge findings with one root cause.Plain code plus agents. String or file-path matching is not enough.


TraceFollow dependencies to other repos.If outside input can reach the vulnerable code through another repo, Trace adds hunt tasks in that consumer repo. Needs a cross-repo symbol index and a dependency graph.


FeedbackMake later tasks better.Uses validation failures, shallow runs, and repeated misses to rewrite prompts that are still in the queue.


ReportWrite the human report.Just a script. No model.





Two tools that give hunters autonomy


    
  
  • Sibling forking. A hunter that finds an interesting path outside its task does not wander off. It calls a tool that starts a sibling agent for that path. This is about 9% of tasks fleet-wide, from near zero to about a fifth depending on the model.
    • 
  
  • The wishlist. When an agent needs something it does not have (a FreeBSD VM, a build environment, production config files), it writes a request with enough context to re-run the task later. It was written 25,472 times across 128 repos and was the most-used tool in the system. One request: "I need a FreeBSD VM to confirm this PoC end-to-end."
    • 



Lesson: watch what agents actually use. Cloudflare connected Semgrep (a static-analysis tool) through the whole system. In a month of runs, hunters called it zero times. They preferred to read and run the code.



VVS stages


    
  
  • Dedup. Comparing every finding with every other finding using a model grows with the square of the count (O(N²)). So plain code first builds indexes over touched files, functions, trust boundaries, and rare words, and gives each finding a short candidate list. Only then does an agent decide whether one fix closes several findings. A stable key across runs makes a re-found bug reopen its old record instead of creating a new one.
    • 
  
  • Judgment. One agent checks whether the code path is reachable in production. It reads deployment and config context, internal wiki, tickets, and git through MCP servers, and checks that the bug still exists on the latest main branch. Output: "exploitable now", "real but latent", or "real but filed against the wrong component".
    • 
  
  • Fixing. The Fixer adapts the proposed patch and test to the repo's style, applies it, and runs the targeted test before and after. It needs a clean fail → pass flip: the test fails before the patch and passes after. If not, the commit is blocked and flagged for a human. The Fixer never merges on its own.
    • 




Rules that make findings trustworthy


Cloudflare lists the ways an AI agent produces fake findings:


    
  
  • It edits the source code so its own exploit works, then reports the bug it just created.
    • 
  
  • It writes a test that proves nothing, such as "exec() executes things, therefore critical vulnerability".
    • 
  
  • It builds an exploit that runs but rests on a nonsense threat model.
    • 



The rules that stop this:


    
  
  1. Threat model first. Before filing, the hunter states who the attacker is and which boundary or assumption breaks. The output schema puts these fields first, so the model must write them before the finding.
    2. 
  
  2. PoC as a test against untouched code. Every confirmed finding includes a test that runs against the original codebase. No working PoC means the finding is treated as fake.
    3. 
  
  3. A patch with every finding. What reaches the review queue is a verified bug, a working test, and a git diff.
    4. 
  
  4. Plain-code checks before any model judges. Code (not a model) checks that cited files and paths exist and that the patch and test parse.
    5. 
  
  5. A validator that cannot file findings. Its only job is to disprove the hunter.
    6. 
  
  6. A different model for triage. Model B judges model A's output.
    7. 




Engineering lessons



  
Persistence before parallelism. Every stage writes to one SQLite database keyed by (run_id, repo, stage). Any stage can resume, retry, or join a later run. Findings are saved as they appear.

  
Keep each agent's job small. Cloudflare keeps each agent below 25% of its context window. A "read all files" approach goes over that limit every time.

  
An error can look like success. Some API errors come back as text inside a normal 200 OK response, not as an exception. Classify the response text, or empty runs get logged as successes.

  
Zero findings is a warning. A hunt that ends fast, with no sub-hunts or gap tasks, usually means a crashed dependency. Mark hunters with zero findings "shallow" and queue them again.

  
Docker needs two flags. If the harness runs inside Docker, the nested sandbox needs seccomp=unconfined and apparmor=unconfined, or it silently fails to start.

  
Budget per repo, not per run. Cost per repo varies widely. Cloudflare caps tasks per repo and uses a pool of 50 to 200 workers. Almost all spend is in the hunt. Each Gapfill pass costs about half the first hunt.

A code sketch of the minimal harness


This sketch shows the shape of Recon → Hunt → Validate with state in SQLite. It is not a product. call_model is a placeholder for your provider's API. Read it for the structure: resumable tasks, two different models, the mechanical check, and the "200 OK but failed" check.


# harness_sketch.py — the shape of a minimal harness, not a product.
import sqlite3, json, pathlib

HUNT_MODEL, VALIDATE_MODEL = "model-a", "model-b"   # different models on purpose
db = sqlite3.connect("harness.db")
db.executescript("""
CREATE TABLE IF NOT EXISTS tasks(run_id, repo, stage, unit, status, result,
  PRIMARY KEY(run_id, repo, stage, unit));
CREATE TABLE IF NOT EXISTS findings(fingerprint PRIMARY KEY, repo, verdict, record);
""")

def call_model(model, prompt):
    raise NotImplementedError("your provider client goes here")

def looks_failed(text):
    # A transient error can arrive as text in a 200 OK response.
    t = text.strip().lower()
    return not t or t.startswith(("error", "rate limit", "overloaded", "internal server"))

def run_task(run_id, repo, stage, unit, model, prompt):
    key = (run_id, repo, stage, unit)
    row = db.execute("SELECT status, result FROM tasks WHERE run_id=? AND repo=? AND stage=? AND unit=?", key).fetchone()
    if row and row[0] == "done":
        return json.loads(row[1])                 # resume: never redo finished work
    text = call_model(model, prompt)
    if looks_failed(text):
        db.execute("INSERT OR REPLACE INTO tasks VALUES (?,?,?,?, 'retry', NULL)", key); db.commit()
        return None
    db.execute("INSERT OR REPLACE INTO tasks VALUES (?,?,?,?, 'done', ?)", (*key, text)); db.commit()
    return json.loads(text)                       # prompts demand JSON only

def cited_code_exists(repo, finding):
    # Plain code, not a model: every cited file and line must exist.
    for step in finding["trace"]:
        f = pathlib.Path(repo, step["file"])
        if not f.is_file() or step["line"] > len(f.read_text(errors="ignore").splitlines()):
            return False
    return True

def audit(run_id, repo):
    recon = run_task(run_id, repo, "recon", "all", HUNT_MODEL, RECON_PROMPT.format(repo=repo))
    for unit in recon["units"]:                   # unit = surface x boundary x attack class
        hunt = run_task(run_id, repo, "hunt", unit["id"], HUNT_MODEL,
                        HUNT_PROMPT.format(unit=json.dumps(unit)))
        for cand in (hunt or {}).get("candidates", []):
            if not cited_code_exists(repo, cand):
                continue                          # reject before any model judges it
            verdict = run_task(run_id, repo, "validate", cand["fingerprint"], VALIDATE_MODEL,
                               VALIDATE_PROMPT.format(candidate=json.dumps(cand)))
            if verdict:
                db.execute("INSERT OR REPLACE INTO findings VALUES (?,?,?,?)",
                           (cand["fingerprint"], repo, verdict["verdict"], json.dumps(cand)))
                db.commit()


The prompts carry the security knowledge. A starting point for each, based on the skill:




HUNT_PROMPT
You are assigned one unit: {unit}.
Read the code at depth. Work from a concrete
invariant:
1. Name the lower-trust principal.
2. Name the accepted input or action.
3. Find the control that should stop it.
4. Trace the exact path after that control.
5. Stop at the smallest dummy-data effect.
6. State a source fix and a regression test.
State the threat model BEFORE the finding.
Return JSON only: {"units":[...],
 "candidates":[...], "hardening":[...]}


VALIDATE_PROMPT
You did not write this candidate:
{candidate}
Try to REFUTE it from source.
1. Check every file, line, and scope.
2. Confirm the first step is a real
   lower-trust entry point.
3. Find the strongest control on the path.
4. Do not invent a stronger result.
You may not report new findings.
Return JSON only:
{"verdict":"confirmed|needs_validation|
  rejected", "reason":"..."}




To grow the sketch, add the parts in Cloudflare's order of need: a coverage table and a Gapfill loop when one pass misses too much; a PoC-and-patch requirement and a sandbox when you want proof; a dedup step when duplicates waste review time; cross-repo tracing when more than one repo matters.



How Cloudflare measures it


There is no list of every real bug in a codebase, so no one can measure true recall (the share of real bugs found). Cloudflare does not claim a false-negative rate. They watch two proxies: whether re-runs keep finding new bugs (they do), and whether coverage keeps growing. The main goal is to keep the number of unconfirmed findings that reach a human as close to zero as possible.
